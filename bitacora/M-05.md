# M-05 — Robustez ante caída de la base de datos, contenedores endurecidos y smoke test

## Incidencia
Mejora posterior a las pruebas P1–P6. Agrupa las limitaciones que el informe técnico dejó registradas
(sección 8, "Limitaciones") y otras detectadas al revisar la configuración final:

1. `GET /items` sin manejo de errores: con PostgreSQL caído respondía **500** en vez de 503.
2. `/health` incluía en la respuesta pública el mensaje interno de la excepción.
3. `main.py` usaba APIs obsoletas: `@app.on_event("startup")` y `datetime.utcnow()`.
4. El proceso del backend corría como `root` dentro del contenedor.
5. Nginx revelaba su versión exacta y no enviaba cabeceras de seguridad ni `X-Forwarded-For`.
6. El campo de texto del frontend no tenía el mismo límite (80) que valida el backend.
7. La verificación funcional se hacía con comandos `curl` sueltos, sin una prueba repetible.

## Síntoma
Con `docker compose stop db`, `GET /api/items` devolvía `Internal Server Error` (HTTP 500) y un traceback en el log,
mientras que `/api/health` devolvía 503 con el texto completo de la excepción de psycopg2.

Esto confirma con una prueba real la limitación que el informe había inferido solo leyendo el código.

## Causa raíz
- Solo `/health` capturaba excepciones. En `/items`, la `OperationalError` de SQLAlchemy llegaba sin manejar a FastAPI, que responde 500.
- En `/health`, `detail=f"database unavailable: {exc}"` copiaba el mensaje interno a la respuesta HTTP.
- `on_event` y `utcnow()` están marcados como obsoletos en FastAPI y en Python 3.12.
- La imagen `python:3.12-slim` ejecuta como `root` si el Dockerfile no indica `USER`.
- Nginx envía `server_tokens on` por defecto y no agrega cabeceras de seguridad.

## Elemento modificado
`backend/main.py`, `backend/Dockerfile`, `frontend/nginx.conf`, `frontend/index.html`, `scripts/smoke_test.sh` (nuevo), `README.md`, `.gitignore`.

## Justificación
- Un **manejador global** de `OperationalError` corrige la causa en todos los endpoints a la vez, no solo en `/items`.
  Así, "base de datos caída" siempre es 503 (servicio no disponible, temporal) y no 500 (error del programa).
- El detalle del error se sigue registrando en el **log** (lo necesario para diagnosticar, como en P5), pero no se expone al cliente.
- `lifespan` es el mecanismo vigente de FastAPI para el inicio y cierre; `engine.dispose()` cierra las conexiones al detener el contenedor.
- `USER appuser`: si alguien compromete la API, no obtiene `root` dentro del contenedor. La app solo lee `/app` y escucha en el 8000 (>1024), así que no necesita privilegios.
- Las cabeceras de Nginx son estándar y no cambian el funcionamiento. `X-Forwarded-For` permite que el backend vea la IP real del cliente detrás del proxy.
- El smoke test hace que la verificación sea **repetible con un solo comando**, en lugar de depender de `curl` manuales.

## Impacto si no se corrige
Ante una caída de PostgreSQL, el frontend recibiría errores 500 que no distinguen una falla temporal de un error de código.
Además, la API expondría detalles internos, el contenedor del backend seguiría corriendo como `root`
y las APIs obsoletas podrían dejar de funcionar al actualizar FastAPI o Python.
