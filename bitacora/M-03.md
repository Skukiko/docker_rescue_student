# M-03 — Nginx resistente a la ausencia o recreación del backend

## Incidencia
Mejora de resiliencia. Con `proxy_pass http://backend:8000/;` (estático), Nginx resuelve el nombre
`backend` **una sola vez, al arrancar**. Si en ese momento el backend no existe, Nginx no arranca.
Si el backend se recrea con otra IP, Nginx sigue apuntando a la IP vieja.

## Síntoma
Con el backend detenido, reiniciar el frontend tumba **toda** la aplicación, incluida la página estática.

## Evidencia
Archivo: `evidencias/M-03_diagnostico.txt`
```
$ docker compose stop backend
$ docker compose restart frontend
$ docker compose ps -a
aci606-rescue-backend-1    ...   Exited (0) 5 seconds ago
aci606-rescue-frontend-1   ...   Restarting (1) Less than a second ago
$ docker compose logs frontend --since 30s | grep -E "emerg|host not found"
frontend-1  | 2026/11/18 15:33:10 [emerg] 1#1: host not found in upstream "backend" in /etc/nginx/conf.d/default.conf:13
$ docker inspect --format 'Status={{.State.Status}} RestartCount={{.RestartCount}}' aci606-rescue-frontend-1
Status=restarting RestartCount=6
$ curl -sS --max-time 3 -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8080/
curl: (7) Failed to connect to localhost port 8080 after 0 ms: Couldn't connect to server
```
Con `restart: unless-stopped` (M-02), Nginx entra en un bucle de reinicios mientras falte el backend.

## Causa raíz
Un host literal en `proxy_pass` se resuelve en la carga de la configuración. Un contenedor detenido no tiene
registro DNS en la red de Docker, así que la carga falla (`[emerg]`) y Nginx termina.

## Elemento modificado
`frontend/nginx.conf`, `frontend/Dockerfile` y `compose.yaml` (servicio `frontend`).

## Cambio aplicado
```diff
--- a/frontend/nginx.conf
+++ b/frontend/nginx.conf
     location /api/ {
-        proxy_pass http://backend:8000/;
+        # Resolver DNS embebido de Docker: el nombre se resuelve en cada petición
+        # (no al arrancar), así Nginx inicia aunque el backend no exista todavía.
+        resolver 127.0.0.11 valid=10s ipv6=off;
+        # BACKEND_HOST/BACKEND_PORT se sustituyen con envsubst al iniciar el contenedor.
+        set $backend_upstream http://${BACKEND_HOST}:${BACKEND_PORT};
+        # Con proxy_pass por variable se quita el prefijo /api/ a mano.
+        rewrite ^/api/(.*)$ /$1 break;
+        proxy_pass $backend_upstream;
         proxy_set_header Host $host;
         proxy_set_header X-Real-IP $remote_addr;
     }
--- a/frontend/Dockerfile
+++ b/frontend/Dockerfile
-COPY nginx.conf /etc/nginx/conf.d/default.conf
+# La imagen oficial procesa /etc/nginx/templates/*.template con envsubst y
+# escribe el resultado en /etc/nginx/conf.d/ al arrancar.
+COPY nginx.conf /etc/nginx/templates/default.conf.template
+ENV BACKEND_HOST=backend \
+    BACKEND_PORT=8000
--- a/compose.yaml
+++ b/compose.yaml
       - "${FRONTEND_PORT:-8080}:80"
+    environment:
+      BACKEND_HOST: backend
+      BACKEND_PORT: "8000"
```

## Justificación
- Si `proxy_pass` contiene una **variable**, Nginx resuelve el nombre en cada petición usando `resolver`.
  `127.0.0.11` es el DNS embebido de Docker. `valid=10s` limita el caché, de modo que una IP nueva tras recrear el backend se ve en ≤10 s.
  `ipv6=off` evita consultas AAAA en una red solo IPv4.
- Con una variable, `proxy_pass` ya no reemplaza el prefijo de la `location`, así que `rewrite ... break` quita `/api/`
  y conserva el comportamiento de R-07 (`/api/health` → `/health`).
- El `20-envsubst-on-templates.sh` de la imagen oficial solo sustituye variables **definidas** en el entorno,
  así que `$host`, `$remote_addr`, `$1` y `$backend_upstream` quedan intactos.
- El destino es configurable sin reconstruir la imagen; el `ENV` del Dockerfile da valores por defecto y `compose.yaml` los hace explícitos.

/      HTTP 200

### Recuperación sin reiniciar Nginx
frontend StartedAt antes: 2026-11-18T15:33:59.193370681Z
$ docker compose start backend
$ curl -sS http://localhost:8080/api/health
{"status":"ok","database":"reachable"}  HTTP 200

La falla del backend queda limitada a `/api/` (502, con error a nivel `[error]` y no `[emerg]`), la página sigue
disponible, y la recuperación ocurre sola sin reiniciar Nginx (`StartedAt` sin cambios).

## Impacto si no se corrige
Un reinicio del frontend con el backend caído (por ejemplo, al reiniciar el host o desplegar) deja toda la aplicación fuera de servicio
en bucle de reinicios, y recrear el backend puede dejar a Nginx con una IP obsoleta.
