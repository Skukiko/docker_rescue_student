# R-05 — `depends_on` simple no espera a que PostgreSQL acepte conexiones

## Incidencia
`depends_on: [db]` solo garantiza que el contenedor `db` se haya **iniciado**, no que PostgreSQL esté
listo. Si el backend arranca antes que la base de datos (o la base de datos no está disponible), el evento
`startup` falla, el backend termina y nadie lo vuelve a levantar.

## Síntoma
Con db detenido, el backend termina con `Exited (3)` y sigue caído aunque la base de datos vuelva.

## Evidencia
Prueba controlada; archivo `evidencias/R-05_diagnostico.txt`:
```
$ docker compose stop db
$ docker compose restart backend
$ docker compose ps -a
docker_rescue_student-backend-1    ...   Exited (3) 5 seconds ago
docker_rescue_student-db-1         ...   Exited (0) 6 seconds ago
$ docker inspect --format 'RestartCount={{.RestartCount}} Policy={{.HostConfig.RestartPolicy.Name}} ExitCode={{.State.ExitCode}}' docker_rescue_student-backend-1
RestartCount=0 Policy=no ExitCode=3
$ docker compose logs backend --tail 3
backend-1  | ERROR:    Application startup failed. Exiting.
$ docker compose start db
$ docker compose ps -a  (10 s después de iniciar db)
docker_rescue_student-backend-1    ...   Exited (3) 16 seconds ago
docker_rescue_student-db-1         ...   Up 10 seconds
$ docker compose logs db | grep -E "init process complete|ready to accept"
db-1  | 2026-11-18 15:23:09.020 UTC [40] LOG:  database system is ready to accept connections
db-1  | PostgreSQL init process complete; ready for start up.
db-1  | 2026-11-18 15:23:09.601 UTC [1] LOG:  database system is ready to accept connections
db-1  | 2026-11-18 15:26:09.786 UTC [1] LOG:  database system is ready to accept connections
```
Los logs de db muestran que, en la primera inicialización, PostgreSQL levanta un servidor **temporal**
(PID 40) para ejecutar los scripts de init, lo apaga y luego arranca el definitivo (PID 1). Durante ese
intervalo el contenedor está "Up" pero la base de datos no siempre acepta conexiones.

## Causa raíz
La forma corta de `depends_on` equivale a `condition: service_started`, como muestra `docker compose config`
en `evidencias/01_config.txt`. No hay healthcheck en db, así que Compose no tiene cómo saber cuándo está lista.
Además, el backend no tiene política de reinicio (`Policy=no`): si falla al arrancar, no se recupera.

## Elemento modificado
`compose.yaml`: `healthcheck` en `db`; `depends_on` del `backend` con `condition: service_healthy`.

## Cambio aplicado
```diff
diff --git a/compose.yaml b/compose.yaml
index 3fa7de9..a6d8b74 100644
--- a/compose.yaml
+++ b/compose.yaml
@@ -11,7 +11,8 @@ services:
     environment:
       DATABASE_URL: "postgresql://appuser:rescue123@db:5432/appdb"
     depends_on:
-      - db
+      db:
+        condition: service_healthy
 
   db:
     image: postgres:16-alpine
@@ -19,3 +20,8 @@ services:
       POSTGRES_USER: appuser
       POSTGRES_PASSWORD: rescue123
       POSTGRES_DB: appdb
+    healthcheck:
+      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
+      interval: 5s
+      timeout: 3s
+      retries: 10
```

## Justificación
`pg_isready` viene incluido en la imagen `postgres` y comprueba que el servidor acepta conexiones.
`$$` escapa la interpolación de Compose para que la variable se expanda **dentro** del contenedor
con sus propios valores. Con 10 reintentos cada 5 s hay hasta ~50 s de margen para la primera inicialización.
La política de reinicio para recuperarse de caídas posteriores se agrega en M-02.

Compose espera a que db esté `Healthy` antes de iniciar el backend.

## Impacto si no se corrige
Arranque intermitente según el orden y la velocidad del equipo: el backend puede quedar caído en
un arranque en frío y no se recupera solo.
